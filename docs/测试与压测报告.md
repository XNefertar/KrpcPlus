## 1. 测试概述

### 1.1 测试背景

Xrpc 是一个自研高性能分布式 RPC 框架，核心设计目标包括：

- 双协议兼容（Legacy 协议 + XRpc 新协议），同一端口自动识别
- 基于 ZooKeeper 的服务发现 + RCU 无锁路由缓存
- Muduo 多 Reactor 网络模型 + RoundRobin/Random 负载均衡
- 9 阶段全链路耗时统计 + 固定桶直方图分位数分析

在提交 `feature/qps-enhancement` 分支之前，需要全面验证各模块的功能正确性与高并发下的性能表现。

### 1.2 测试目标

| 目标 | 说明 |
|------|------|
| **功能正确性** | 验证所有 RPC 方法（Login/Register）在双协议下的端到端正确性 |
| **协议兼容性** | 验证 Legacy 与 XRpc 协议在同一端口下的自动识别与正确解析 |
| **服务发现** | 验证 ZK 服务注册、路由缓存、Watcher 触发路由更新的完整流程 |
| **负载均衡** | 验证 Random 与 RoundRobin 两种策略的分布均衡性 |
| **高并发吞吐** | 测量 100 并发线程 × 10000 次调用的 QPS、延迟与成功率 |
| **全链路耗时** | 验证 9 阶段分桶直方图的统计准确性、瓶颈诊断与长尾告警 |
| **路由表性能** | 对比 RCU / RwLock / Mutex 在"多读少写"场景下的长尾延迟 |

### 1.3 测试环境

| 项目 | 配置 |
|------|------|
| **操作系统** | macOS 14.x (ARM64 / Apple Silicon) |
| **编译器** | Apple Clang (C++17, `-O2` 优化) |

## 3. 压测实现思路

### 3.1 压测场景设计

压测分为两个层次：

| 层次 | 工具 | 场景 | 目的 |
|------|------|------|------|
| **L1: 组件级** | `rcu_benchmark` | 8 读线程 + 1 写线程，变频率写 | 对比 RCU / RwLock / Mutex 的读长尾延迟 |
| **L2: 端到端** | `qps_benchmark` | 50~100 并发线程 × 1000~10000 次调用 | 测量整体 QPS / 延迟 / 成功率 |
| **L3: 全链路** | `benchmark_stats` | 8 线程模拟 9 阶段耗时分布 | 验证分位数统计 + 瓶颈诊断 + 长尾告警 |

#### 场景参数设计逻辑

- **线程数选择 50~100**: 模拟中等规模 RPC 客户端的并发度，覆盖典型的线程池大小
- **写频率 1/s~500/s**: 覆盖 ZK 回调的低频场景（1/s）到极端路由抖动场景（500/s）
- **3% 长尾注入**: 模拟生产环境中 TCP 重传 / GC 暂停 / CPU 调度导致的尾延迟
- **测试时长 5 秒**: 平衡统计意义与执行时间，采样间隔 500ms~1s 获取足够样本

### 3.2 关键性能指标定义

| 指标 | 定义 | 计算方法 |
|------|------|------|
| **Overall QPS** | 总请求数 / 总耗时 | `(success + fail) / elapsed_seconds` |
| **Interval QPS** | 每秒窗口内的瞬时 QPS | `delta_total / interval_seconds` |
| **Peak QPS** | 所有采样窗口的最高 QPS | `max(interval_qps_history)` |
| **QPS Stability** | QPS 波动稳定度 | `(1 - stddev / avg) × 100%` |
| **Success Rate** | 成功请求占比 | `success / (success + fail) × 100%` |
| **Avg Latency** | 所有成功请求的平均端到端延迟 | `total_latency_us / success_count`（微秒） |
| **P50/P95/P99** | 9 阶段分桶直方图中的分位数 | 桶中点 × 桶序号，累计和首次跨阈值 |
| **P999/P50 ratio** | 长尾放大倍数 | `P999_ns / P50_ns`，>10x 表示严重长尾 |
| **Concurrency Efficiency** | 实际 QPS / 理论最大 QPS | `(QPS × avg_latency / threads / 1000) × 100%` |

### 3.3 并发模型构建

#### L1 组件级 (rcu_benchmark)

```
                    ┌──────────────────────┐
                    │   共享路由表 (Atomic)  │
                    └──┬────────┬────────┬─┘
           ┌──────────┘        │        └──────────┐
           ▼                   ▼                   ▼
    ┌────────────┐     ┌────────────┐      ┌────────────┐
    │ 读线程 ×8  │     │ 读线程 ×8  │ ...  │ 写线程 ×1  │
    │ path_idx++ │     │ path_idx++ │      │ COW + 替换 │
    │ atomic_load│     │ atomic_load│      │ 1~500次/s  │
    └────────────┘     └────────────┘      └────────────┘
```

关键设计：
- 8 个读线程各自使用 `path_idx = thread_id × 13 % 100` 的不同起始偏移，避免同路径热点
- 1 个写线程以固定频率（1/s, 100/s, 500/s）执行 COW 替换
- 读操作每隔 1000 次记录一个延迟样本（ns 精度），避免样本量过大导致内存膨胀
- 三种方案（RCU / RwLock / Mutex）在完全相同的硬件和时间窗口下分别运行

#### L2 端到端 (qps_benchmark)

```
    main()
      │
      ├─ [monitor 线程] ── 每 500ms 采样 ── 实时 QPS / 成功率 / 延迟输出
      │
      ├─ [worker 线程 ×50~100]
      │     ├─ 1000~10000 次模拟 RPC
      │     ├─ LatencySimulator::SimulateCall() (9 阶段 sleep 模拟)
      │     ├─ 0.5% 模拟失败率
      │     └─ atomic fetch_add 累加 success/fail/latency
      │
      └─ [主线程] ── 等待 workers 完成 ── 统计报告
```

#### L3 全链路 (benchmark_stats)

模拟一次完整 RPC 的 9 阶段耗时分布：

| 阶段 | 耗时分布 | 说明 |
|------|------|------|
| ZK_QUERY | Normal(2.0, 0.8) ms | 首次查 ZK |
| LOAD_BALANCE | Normal(0.001, 0.0005) ms | atomic 操作 |
| CONNECT | Normal(0.5, 0.3) ms | TCP 建连 (仅首次) |
| SERIALIZE_REQ | Normal(0.015, 0.008) ms | Protobuf 序列化 |
| ENCODE_REQ | Normal(0.005, 0.003) ms | 协议编码 |
| NET_IO | Normal(0.2, 0.15) ms + 3% 长尾 | 网络 RTT |
| DECODE_RES | Normal(0.005, 0.003) ms | 协议解码 |
| DESERIALIZE_RES | Normal(0.012, 0.006) ms | Protobuf 反序列化 |
| TOTAL | 上述阶段之和 | 端到端总耗时 |

### 3.4 测试数据准备

**请求数据**:
- LoginRequest: `name="zhangsan"`, `pwd="123456"`
- RegisterRequest: `id=1`, `name="lisi"`, `pwd="654321"`
- 所有请求体均使用 Protobuf 3 序列化，content_type=Protobuf

**路由表数据**:
- 模拟 100 个服务路径（`/Service0/Method` ~ `/Service99/Method`）
- 每个路径 10 个节点（`10.0.0.0:8000` ~ `10.0.0.9:8000`）
- 使用 `std::unordered_map<string, vector<string>>` 存储

### 3.5 压测工具设计

| 工具 | 源码 | 零依赖 | 编译方式 |
|------|------|:---:|------|
| `qps_benchmark` | `tools/qps_benchmark.cc` | ✅ | `g++ -std=c++17 -O2 -lpthread` |
| `benchmark_stats` | `tools/benchmark_stats.cc` | - | 链接 `runtime_stats.cc` |
| `rcu_benchmark` | `tools/rcu_benchmark.cc` | ✅ | `g++ -std=c++17 -O2 -lpthread` |
| `bench_client` | `example/caller/bench_client.cc` | - | CMake 构建，链接 xrpc_core |

设计原则：
1. **零外部依赖**: `qps_benchmark` 和 `rcu_benchmark` 仅依赖 C++17 标准库 + pthread，可直接 `g++` 编译，无需 CMake 配置
2. **原子计数**: 所有统计计数器使用 `std::atomic<long long>` + `memory_order_relaxed`，最小化同步开销
3. **实时监控**: 独立监控线程每 500ms 输出一次 QPS 快照，不影响 Worker 线程的关键路径
4. **分位数计算**: 使用全量排序（小样本）或固定桶直方图（大样本）计算 P50/P95/P99

- 第 5 段 QPS 下降至 115k（约 -13%），原因是大量线程在最后阶段陆续完成，剩余并发度降低

### 4.3 路由表 RCU vs RwLock vs Mutex 对比

**测试配置**: 8 读线程 + 1 写线程（分别以 500/s、100/s、1/s 频率写入），每个样本间隔 1000 次读

#### 高写压力 (500/s)

| 方案 | P50 | P99 | P999 | P999/P50 | 相对 RCU 的 P999 |
|------|:---:|:---:|:---:|:---:|:---:|
| **RCU** | ~0μs | 27.2μs | **69.0μs** | 1643x | 基准 |
| RwLock | ~0μs | 26.9μs | 87.5μs | 2083x | +26.8% |
| Mutex | ~0μs | 25.7μs | 82.0μs | 1953x | +18.8% |

#### 中写压力 (100/s)

| 方案 | P50 | P99 | P999 | P999/P50 | 相对 RCU 的 P999 |
|------|:---:|:---:|:---:|:---:|:---:|
| **RCU** | ~0μs | 25.8μs | **71.0μs** | 1692x | 基准 |
| RwLock | ~0μs | 27.0μs | 88.7μs | 2112x | +24.9% |
| Mutex | ~0μs | 24.4μs | 80.8μs | 1925x | +13.8% |

#### 低写压力 (1/s)

| 方案 | P50 | P99 | P999 | P999/P50 | 相对 RCU 的 P999 |
|------|:---:|:---:|:---:|:---:|:---:|
| **RCU** | 0.1μs | 26.0μs | **64.3μs** | 775x | 基准 |
| RwLock | 0.1μs | 27.8μs | 92.4μs | 1113x | +43.7% |
| Mutex | ~0μs | 25.7μs | 82.6μs | 1967x | +28.5% |

**综合结论**:

1. **P50/P99 三类方案几乎持平**（均在 0~30μs 范围），因为 `unordered_map::find()` 在 100 条目的规模下已被优化到纳秒级，锁开销淹没在调度噪声中
2. **RCU 的 P999 始终最低**，比 RwLock 低 21%~44%，比 Mutex 低 14%~28%
3. **写压力越低，RCU 优势越大**——1/s 时 RCU 比 RwLock 低 43.7%，因为低写压力下 RwLock 的快速路径优势消失，而 RCU 的一致性快照语义避免了锁开销抖动
4. **平台限制**: macOS libc++ 上 `std::atomic_load<shared_ptr>` 非 lock-free（使用内部 spinlock），在 Linux libstdc++ 上差距预期更大

### 4.4 系统瓶颈评估

| 瓶颈层级 | 瓶颈点 | 影响程度 | 说明 |
|:---:|------|:---:|------|
| **网络** | TCP 建连 + 数据包 RTT | ⭐⭐⭐⭐⭐ | 占端到端耗时的 70%+，是首要瓶颈 |
| **序列化** | Protobuf SerializeToString | ⭐⭐ | 小消息下 <50μs，大消息会成为瓶颈 |
| **服务发现** | ZK 首次查询 | ⭐⭐ | 冷启动约 2ms，缓存命中后 <1μs |
| **编解码** | Peek/Skip + Protobuf Parse | ⭐ | 均在 5~12μs，非瓶颈 |
| **负载均衡** | atomic fetch_add | ⭐ | <1μs，可忽略 |
| **路由缓存** | atomic_load + COW | ⭐ | 读路径 <50ns（P50），P999 控制在 70μs 内 |

## 5. 优化建议

基于压测结果，提出以下优化建议：

| 优先级 | 优化项 | 预期收益 | 实现难度 |
|:---:|------|:---:|:---:|
| P0 | 引入连接池，消除 CONNECT 阶段开销 | P50 延迟降低 ~40% | 中 |
| P1 | 服务发现预热（后台异步刷新路由表） | 消除冷启动首请求 2ms 延迟 | 低 |
| P2 | 协议编码直接写入 socket buffer，减少中间拷贝 | NET_IO 外减少 5~12μs | 中 |
| P3 | 使用 folly::atomic_shared_ptr 替换 std::atomic_load（需引入 folly） | RCU 读延迟降低至真正 lock-free | 高 |
| P4 | 自适应长尾告警阈值（P99 - P95 > 5ms 且 P99/P95 > 2x） | 减少误报 | 低 |
