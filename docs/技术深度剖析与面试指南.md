## 2. 模块一：双协议兼容的零拷贝编解码器

### 2.1 挑战

设计一个 RPC 框架时，协议兼容性是绕不开的问题。一方面，简单的二进制协议（Legacy）易于实现和调试；另一方面，现代 RPC 需要流式传输、多压缩算法、调用链透传等能力。**如果在不同端口部署新旧协议，调用方需要改路由、改配置，迁移成本高且容易出错。**

### 2.2 解决方案

#### 2.2.1 协议帧格式对比

```
Legacy 协议:                         XRpc 新协议:
┌────────────┬────────────┬─────┐    ┌──────────────┬──────────────┬─────┐
│ TotalLen   │ HeaderLen  │Body │    │ FixedHeader  │  VarHeader   │Body │
│   (4B BE)  │  (4B BE)   │     │    │   (16B)      │ (Protobuf)   │     │
└────────────┴────────────┴─────┘    └──────────────┴──────────────┴─────┘

                                       FixedHeader 字段:
                                       ┌───────┬──────┬───────────┬──────┐
                                       │ Magic │ Type │StreamType │ ...  │
                                       │ (2B)  │ (1B) │  (1B)     │      │
                                       └───────┴──────┴───────────┴──────┘
                                       magic = 0x5850 ('X''P' 的 ASCII)
```

#### 2.2.2 协议自动识别 — CodecFactory

```cpp
// codec_factory.cc — 核心逻辑仅 7 行
std::unique_ptr<ServerCodec> CodecFactory::CreateServerCodec(
    const NoncontiguousBuffer& in) {
  if (in.ReadableBytes() >= 2) {
    uint16_t magic = ntohs(*(uint16_t*)in.Peek(2));  // Peek 不消费数据
    if (magic == kMagicNumber) {
      return CreateXRpcServerCodec();  // magic=0x5850 → XRpc
    }
  }
  return std::make_unique<LegacyServerCodec>();  // 其他 → Legacy
}
```

**设计要点**：
- 只 Peek 前 2 字节，不消费数据，失败可回退
- 代价仅一次 `ntohs` + 整数比较，< 10ns
- 对业务代码完全透明 — `ProtocolMessage` 统一抽象

#### 2.2.3 零拷贝解码 — Peek/Skip 两阶段

```cpp
// 第一遍: CheckAndPick — 校验帧完整性，不拷贝数据
int CheckAndPick(conn, buf) {
  if (buf.ReadableBytes < kFixedHeaderSize) return 0;  // 半包等待
  PeekFixedHeader(buf, fh);                             // 只读偏移
  if (!fh.IsValid())         return kCodecInvalidMagic;
  if (fh.total_size > kMax)  return kCodecOversized;
  if (buf.ReadableBytes < fh.total_size) return 0;     // 帧未到齐
  return fh.total_size;                                 // 返回整帧长度
}

// 第二遍: ZeroCopyDecode — Peek 填充字段，Skip 消费整帧
int ZeroCopyDecode(conn, buf, msg) {
  msg.body.resize(fh.BodySize());
  buf.Peek(&msg.body[0], BodySize, offset=kFixedHeaderSize + header_size);
  // ... 解析 Protobuf 可变头 ...
  buf.Skip(fh.total_size);  // 一次性消费整帧
}
```

**为什么是两遍而非一遍**：第一遍用于 TCP 拆包判断（半包 vs 完整帧），不产生任何堆分配。只有确认帧完整后才在第二遍创建 `ProtocolMessage` 并拷贝数据。

#### 2.2.4 防攻击的边界检查 — 一个容易遗漏的细节

```cpp
// header_size 来自网络，攻击者可伪造为 65535
// 如果不检查就计算 body_len = total_size - kFixedHeaderSize - header_size
// → 无符号下溢 → 巨大的正数 → Peek 越界读取 → segfault

if (fh.header_size > fh.total_size - kFixedHeaderSize) {
    return kCodecParseError;  // ← 这道检查防止了堆缓冲区溢出
}
```

### 2.3 数据

| 指标 | 数值 |
|------|------|
| 协议识别开销 | < 10ns (一次 ntohs + int compare) |
| 编解码延迟 | Encode ~5μs, Decode ~5μs |
| 支持的序列化类型 | Protobuf / JSON / FlatBuffers (枚举预留) |
| 支持的压缩算法 | None / Gzip / Snappy / LZ4 (枚举预留) |
| 透传字段 | `map<string,string> trans_info` (tracing / 染色 / 自定义标签) |

### 2.4 面试话术

> "我设计了一套协议自识别框架，核心思路是在定长头的 2 字节 magic 做协议路由—收到 XRpc 魔数就创建 XRpcCodec，否则回退 LegacyCodec。同一端口支持两种协议，业务方零改动平滑迁移。解码做了 Peek/Skip 两阶段—第一遍只校验帧完整性不拷贝，第二遍在 NoncontiguousBuffer 上按偏移读取避免 memcpy。另外做了一道 header_size > total 的防下溢检查，防止恶意帧导致堆溢出。"

## 3. 模块二：RCU + COW 无锁路由缓存

### 3.1 挑战

每个 RPC 调用都要查路由表（`/Service/Method → [ip:port, ...]`），是**最热路径**。ZooKeeper Watcher 在节点上下线时触发路由更新——这是经典的"读多写少"并发场景。如果用 `std::shared_mutex`，读操作仍有锁开销，极端情况下写操作会阻塞所有读操作。

### 3.2 解决方案

#### 3.2.1 数据结构

```cpp
class RouteManager {
  // 类型: unordered_map<service_path, vector<ip:port>>
  using RouteTable = std::unordered_map<std::string, std::vector<std::string>>;

  std::shared_ptr<const RouteTable> _curRouteTable;  // 注意: const
  std::mutex _writeMutex;
};
```

**为什么 shared_ptr 要 const**：`const` 承诺"拿到后不可修改"，这是 RCU 语义的基础——读线程拿到快照后，没有人能改变这个快照的内容。

#### 3.2.2 读路径 — 一次原子操作，零锁

```cpp
std::vector<std::string> GetRouteNodes(const std::string& path) const {
  auto local = std::atomic_load(&_curRouteTable);  // [1] 原子快照
  auto it = local->find(path);                      // [2] 在快照上操作
  return (it != local->end()) ? it->second : std::vector<std::string>{};
} // [3] local 析构 → shared_ptr refcount -1
```

**三步关键语义**：
1. `atomic_load` 原子地读取指针 + 增加引用计数，不可打断
2. 后续所有操作都在 `local` 指向的**不可变**快照上进行
3. 函数返回后 `local` 析构，旧表引用计数归零则自动释放

#### 3.2.3 写路径 — COW 拷贝 + 原子替换

```cpp
void UpdateRouteTable(path, zkClient, watch) {
  std::lock_guard<std::mutex> lk(_writeMutex);         // 写写互斥
  auto old = std::atomic_load(&_curRouteTable);         // 拿旧表
  auto newTable = std::make_shared<RouteTable>(*old);   // COW 整表拷贝
  (*newTable)[path] = client->GetChildren(path, watch); // 修改副本
  std::atomic_store(&_curRouteTable,
                    std::shared_ptr<const RouteTable>(newTable)); // 原子替换
}
```

#### 3.2.4 一致性的时间线证明

```
                    _curRouteTable
                         │
T0: ──────────────→ [版本A] refcount=1


T1: 读线程          写线程
    atomic_load    (等待 _writeMutex)
    → local = [A]
    [A] refcount=2


T2: 读线程          写线程拿到锁
    find(path)     newTable = COW(*old)
    操作 [A]       修改 newTable[path]
                   atomic_store → [版本B]
                   [A] refcount=1 (只有 local 持有)


T3: 读线程
    return nodes   ← 返回的是版本A的数据，不受替换影响


T4: 读线程
    local 析构
    [A] refcount=0 → 自动释放

T5: 下一次 RPC 调用
    atomic_load → [版本B]   ← 拿到最新版本
```

**一句话**：`atomic_load` 给读线程拍了张瞬态快照，`shared_ptr` 的引用计数保证快照在读完前不被销毁。

### 3.3 实测数据（macOS ARM64，8 读线程 + 1 写线程）

| 写压力 | 方案 | P999 读延迟 | 比 RCU 慢 |
|:---:|------|:---:|:---:|
| 500/s | **RCU** | **69.0μs** | 基准 |
| | RwLock | 87.5μs | +26.8% |
| | Mutex | 82.0μs | +18.8% |
| 100/s | **RCU** | **71.0μs** | 基准 |
| | RwLock | 88.7μs | +24.9% |
| | Mutex | 80.8μs | +13.8% |
| 1/s | **RCU** | **64.3μs** | 基准 |
| | RwLock | 92.4μs | **+43.7%** |
| | Mutex | 82.6μs | +28.5% |

### 3.4 诚实的重要补充

**`std::atomic_load<shared_ptr>` 在 macOS/libc++ 上并非 lock-free**，内部使用全局 spinlock 保护控制块。这意味着 RCU 只是"把外显的读写锁换成 shared_ptr 内部的隐藏锁"，并未彻底消除锁。差距是真实的但不到数量级——这恰恰说明 RCU 的核心价值不在吞吐量数字，而在于：

1. **写期间读不阻塞**：RwLock 在写线程持 `unique_lock` 做 COW 拷贝时，所有读线程 `shared_lock` 全部排队
2. **const 快照消除 use-after-free**：读线程不会持有已释放的裸指针
3. **无锁升级/降级问题**：避免 `shared_mutex` 在高竞争下的死锁风险

### 3.5 面试话术

> "路由缓存用了 RCU + Copy-on-Write 模式。读路径只一次 `atomic_load<shared_ptr>` + `unordered_map::find`，完全不碰写锁。写路径 COW 拷贝整表然后 `atomic_store` 原子替换。关键是——读线程拿到的 `shared_ptr<const RouteTable>` 是不可变的快照，写线程替换全局指针时不影响正在进行的读操作。实测 RCU 的 P999 长尾比 RwLock 低 20~44%。坦诚说 macOS 上 `atomic_load<shared_ptr>` 非 lock-free，但 RCU 的语义正确性和写不阻塞读的性质，比吞吐量数字更有工程价值。"

## 4. 模块三：多 Reactor I/O 多路复用网络模型

### 4.1 挑战

原始服务端是 **thread-per-connection** 模型：每 accept 一个连接就 `pthread_create` 一个新线程处理。200 个并发连接 = 200 个 OS 线程，频繁的线程创建销毁 + 上下文切换导致：QPS 天花板只能到 ~72k，线程数增加反而降低吞吐量。

### 4.2 解决方案

#### 4.2.1 架构演进

```
原始 (thread-per-connection):           Reactor (poll multiplexing):
                                        
 accept() ──→ thread1 (1个连接)          accept() ──→ Worker0 ──→ poll(fd1,fd2,...)
        ├──→ thread2 (1个连接)                  ├──→ Worker1 ──→ poll(fd3,fd4,...)
        ├──→ thread3 (1个连接)                  ├──→ Worker2 ──→ poll(fd5,fd6,...)
        └──→ ... (200个线程)                    └──→ Worker3 ──→ poll(fd7,fd8,...)
                                                 
 线程数 = 连接数                          线程数 = Worker数 (4)
 上下文切换 = O(连接数)                   上下文切换 = O(Worker数)
```

#### 4.2.2 Worker EventLoop 核心实现

```cpp
void WorkerLoop(int worker_id, WorkerContext* ctx) {
  struct pollfd fds[kMaxFds];  // 每个 Worker 管理最多 4096 个 fd
  int num_fds = 0;

  while (running) {
    // 1. 接收主线程分发的新连接
    {
      std::lock_guard lk(ctx->mtx);
      for (int fd : ctx->new_fds) {
        fds[num_fds++] = {fd, POLLIN, 0};
      }
      ctx->new_fds.clear();
    }

    // 2. poll() 等待就绪事件
    int ready = poll(fds, num_fds, /*timeout=*/1ms);

    // 3. 处理就绪的 fd — 非阻塞读请求 + 处理 + 写响应
    for (int i = 0; i < num_fds && ready > 0; ++i) {
      if (fds[i].revents & POLLIN) {
        ProcessOneRequest(fds[i].fd);  // 读帧 → 解析 → 业务 → 写响应
        counter->fetch_add(1);
      }
    }
  }
}
```

#### 4.2.3 主线程 accept + RoundRobin 分发

```cpp
// Main Thread
int rr_idx = 0;
while (running) {
  int client_fd = accept(listen_fd, ...);
  SetNonBlocking(client_fd);
  setsockopt(client_fd, TCP_NODELAY, 1);  // 禁用 Nagle，减少小包延迟

  int idx = rr_idx++ % num_workers;
  {
    std::lock_guard lk(contexts[idx].mtx);
    contexts[idx].new_fds.push_back(client_fd);
  }
}
```

### 4.3 实测数据（真实 TCP + Protobuf 全链路）

| 客户端线程 | 原始 QPS | Reactor QPS | QPS 提升 | 原始 P50 | Reactor P50 | P50 降低 |
|:---:|------|------|:---:|------|------|:---:|
| 50 | 72,257 | **99,521** | **+37.7%** | 0.663ms | 0.472ms | **-28.8%** |
| 100 | 71,917 | **103,712** | **+44.2%** | 1.359ms | 0.930ms | **-31.6%** |
| 200 | 69,856 | **103,120** | **+47.6%** | 2.775ms | 1.871ms | **-32.6%** |

| Worker 数 | 200线程 QPS | P50 | P999 | 说明 |
|:---:|------|------|------|------|
| 4 | **103,120** | 1.871ms | 10.015ms | QPS 天花板，长尾偏高 |
| 8 | 93,437 | 2.076ms | 5.414ms | 锁竞争增加，QPS 下降但长尾改善 |

**关键发现**：
- QPS 天花板从 72k 提升到 **103k** (+43%)
- P50 延迟降低 **~30%**
- 4 个 Worker 线程完成了原始版 200 个线程的活

### 4.4 面试话术

> "我把 thread-per-connection 模型重写成了 poll() 多路复用—4 个 Worker 线程，每个管理数百个连接。在真实 TCP + Protobuf 链路上 QPS 从 7.2 万提升到 10.3 万，+43%；P50 降低约 30%。核心原理很简单：线程数从 200 降到 4，上下文切换大幅减少。如果换 Muduo 的 epoll/kqueue 替代 poll()，且用 eventfd 替换互斥锁通信，长尾和 QPS 还能进一步提升。"

## 5. 模块四：9 阶段全链路分桶直方图性能剖析

### 5.1 挑战

RPC 调用的端到端延迟是多个环节串联的结果。当线上 P99 突增时，传统监控只能告诉你"慢了"，无法告诉你**慢在哪个环节**——是序列化慢了？网络慢了？还是服务发现慢了？需要定位到具体阶段才能快速修复。

### 5.2 解决方案

#### 5.2.1 9 阶段定义

```cpp
enum Stage {
  ZK_QUERY = 0,       // ZK 查路由表
  LOAD_BALANCE = 1,   // 负载均衡选择节点
  CONNECT = 2,        // TCP 建连
  SERIALIZE_REQ = 3,  // Protobuf 序列化请求
  ENCODE_REQ = 4,     // 协议编码
  NET_IO = 5,         // send + recv 系统调用
  DECODE_RES = 6,     // 协议解码
  DESERIALIZE_RES = 7,// Protobuf 反序列化响应
  TOTAL = 8           // 端到端总耗时
};
```

#### 5.2.2 计时实现 — RAII ScopedTimer

```cpp
class ScopedTimer {
  Stage stage_;
  std::chrono::high_resolution_clock::time_point start_;
public:
  ScopedTimer(Stage s) : stage_(s), start_(Clock::now()) {}
  ~ScopedTimer() {
    auto duration = std::chrono::duration<double, std::milli>(
        Clock::now() - start_).count();
    RuntimeStats::GetInstance().Record(stage_, duration);
  }
};

// 使用方式 — 在代码块开头声明，块结束时自动记录
{
  ScopedTimer t(RuntimeStats::NET_IO);
  send(fd, wire.data(), wire.size(), 0);
  recv_exact(fd, buf, total_len);
} // ← 离开作用域自动记录耗时
```

#### 5.2.3 固定桶直方图 — P50/P95/P99 分位数

```cpp
void RuntimeStats::Record(Stage stage, double duration_ms) {
  // 1. 计数
  m_counts[stage]++;

  // 2. 累计耗时 (纳秒，用于算 avg)
  long long ns = static_cast<long long>(duration_ms * 1e6);
  m_total_times[stage].fetch_add(ns, std::memory_order_relaxed);

  // 3. 更新最大值 (CAS 循环，保证单调递增)
  long long old_max = m_max_times[stage].load();
  while (ns > old_max &&
         !m_max_times[stage].compare_exchange_weak(old_max, ns));

  // 4. 落入直方图桶 (O(1))
  int bucket = static_cast<int>(duration_ms / kBucketWidthMs);
  if (bucket >= kHistBucketCount) bucket = kHistBucketCount - 1;
  m_hist[stage][bucket].fetch_add(1, std::memory_order_relaxed);
}

// 分位数计算: 遍历桶累加，首次超过目标即得
PercentileResult ComputePercentiles(Stage stage) {
  long long target_p50 = count * 0.50;
  long long target_p99 = count * 0.99;
  long long cumulative = 0;
  for (int i = 0; i < kHistBucketCount; ++i) {
    cumulative += m_hist[stage][i].load();
    if (!found_p50 && cumulative >= target_p50)
      result.p50_ms = (i + 0.5) * kBucketWidthMs;  // 桶中点
    if (!found_p99 && cumulative >= target_p99)
      result.p99_ms = (i + 0.5) * kBucketWidthMs;
    // ...
  }
}
```

#### 5.2.4 瓶颈自动诊断 + 长尾告警

### 5.3 为什么选固定桶直方图而非 HDR Histogram

| 考量 | 固定桶直方图 | HDR Histogram |
|------|:---:|:---:|
| 插入开销 | O(1) fetch_add | O(1) CAS |
| P99 精度 | ±0.5 × 桶宽 (0.5ms) | < 0.01% |
| 内存 | O(桶数) 固定 | O(log range) 动态 |
| 实现复杂度 | ~50 行 | ~500+ 行 |
| 依赖 | 零 | 需引入 HdrHistogram_c |

**选择固定桶的理由**：本项目的 RPC 延迟在 0.5~10ms 范围，1ms 桶宽下 P99 误差 ±0.5ms，完全够用。无外部依赖、代码量小、插入路径极度简单（仅 3 次原子操作），是 ROI 最高的方案。

### 5.4 面试话术

> "我在每次 RPC 调用的关键路径上嵌入了 9 个 `ScopedTimer`—利用 RAII 自动计时，离开作用域即记录。统计数据落在一个固定桶直方图里，每个桶是 `atomic<long long>`，插入只需一次 `fetch_add`，对热路径的性能影响 < 0.5%。瓶颈诊断通过 P50 排序 + ASCII bar 可视化，一眼就能看到'NET_IO 占了 71.4%'。长尾告警规则是 P99 > 3×P95 且 P99 > 1ms—双重阈值避免低延迟场景的误报。为什么不用更精确的 HDR Histogram？因为当前延迟范围在 0.5~10ms，1ms 桶宽误差 ±0.5ms 足够定位瓶颈，不需要引入外部依赖。"

### 7.2 STAR 法则包装（以协议编解码为例）

**S (情境)**: 一个 RPC 框架需要同时支持简洁的 Legacy 二进制协议和功能更丰富的 XRpc 新协议（流式传输、多压缩算法、透传字段），不能通过多端口部署来区分。

**T (任务)**: 设计一套编解码框架，同一端口同时服务 Legacy 和 XRpc 客户端，对业务透明。

**A (行动)**: 在 16 字节定长头前 2 字节设 magic，CodecFactory Peek 2 字节判协议。解码分 CheckAndPick + ZeroCopyDecode 两阶段——第一遍不拷贝只校验，第二遍在 NoncontiguousBuffer 上按偏移读取。加了 header_size 防下溢检查防止恶意帧溢出。

**R (结果)**: 业务方零改动完成协议迁移，协议识别 < 10ns，编解码延迟 < 10μs。

### 7.3 常见追问及应答

**Q: RCU 性能提升多少？有 benchmark 吗？**

> 有。macOS 上 8 读线程 + 1 写线程实测：RCU P999=71μs，RwLock P999=89μs，RCU 低约 24%。坦诚说差距不大——因为 `atomic_load<shared_ptr>` 内部有 spinlock。选择 RCU 核心理由不是吞吐量，是写操作不阻塞读+const 快照语义。

**Q: QPS 10 万算高吗？gRPC 能到 50 万+？**

> gRPC 用的是 HTTP/2 多路复用 + 异步 IO，走的是完全不同的架构路径。我这 10 万是在最简单的 poll 多路复用 + 同步 send/recv 上跑的，如果升级到 Muduo Reactor + 单连接多路复用，QPS 还能再提升 3~5 倍。重点是验证了多路复用对 thread-per-connection 模型的碾压性优势。

**Q: 为什么不用现成的 brpc/gRPC？**

> brpc 和 gRPC 是通用框架，学习成本和定制成本高。自研的优势是：协议格式完全可控（16B 定长头 vs gRPC 的 HTTP/2 帧头 9B）、可以和 Legacy 协议无缝兼容、后续接入自研注册中心和监控系统不需要适配层。2000 行核心代码 vs 10 万行通用框架——维护成本不是一个量级。

**Q: 为什么选 ZooKeeper 而不是 etcd？**

> 三个原因。第一，ZK 是 C++ RPC 生态的事实默认选择——brpc、tars 都用它，官方 C 客户端 `libzookeeper_mt` 久经考验，而 etcd 的 C++ 客户端是社区维护的，成熟度差距明显。第二，ZK 的 EPHEMERAL 临时节点直接匹配服务发现需求——进程挂了 TCP 就断，节点自动消失，不需要应用层心跳；etcd 需要 grant Lease + 绑定 key + KeepAlive 续约，概念多、代码多。第三——也是最关键的——RCU 缓存让 ZK 不在热路径上。每次 RPC 调用走的是 `atomic_load` + 内存查表，纳秒级；ZK 只在 cache miss 或节点变更时才被访问。所以 ZK 的 JVM 开销、Watcher 一次性触发这些缺陷，对整体吞吐量没有影响。RouteManager 的接口已经抽象好了，真需要换 etcd，替换 ZookeeperClient 实现就行。

### 7.4 弱点坦诚 — 主动暴露短板

> "当前最明显的短板是客户端仍然用同步阻塞 send/recv——每个 Channel 一个 fd，一次只能跑一个请求。其次负载均衡缺少健康探测和自适应加权，RR 轮询会把流量打到慢节点上。这两个是下一阶段要解决的。"

面试官会更信任一个知道自己代码短板的人。

## 8. 沉淀的通用技术经验

### 8.1 关于协议设计

**"不要把可变性留给二进制协议"**。Legacy 协议的字段位置固定导致无法扩展（要加新字段就得改帧格式）。XRpc 选择"定长头只放不变的基础字段 + Protobuf 管可变头"——既保留了高性能的二进制帧头，又给了业务字段无限扩展的空间。`content_type` / `content_encoding` 用 enum 扩展，`trans_info` 用 map 做完全透传——这是协议设计中最有价值的模式。

### 8.2 关于并发模型

**"无锁不一定是好事，但正确的锁设计一定是好事"**。RCU 方案并没有彻底消除锁（shared_ptr 内部有 spinlock），但它把锁从"每次读都竞争"变成了"真正需要时才竞争"。工程上追求的不是"绝对无锁"，而是在当前规模和当前平台上找到**最简正确方案**。

### 8.3 关于性能优化

**"先跑真实数据，再决定优化方向"**。这个项目最大的教训来自全链路耗时统计——跑出数据之前我觉得序列化是瓶颈，实际数据显示 NET_IO 占了 71.4%。没有再猜，而是先上了全链路计时，用数据说话。这条经验适用于所有性能优化工作。

### 8.4 关于可观测性

**"性能数据不是运维的事，是开发的事"**。9 阶段耗时、瓶颈诊断、长尾告警——这三件事的代码量加起来不到 200 行，但上线后定位一个瓶颈从"人肉二分 printf"变成了一行日志。最小化的可观测性投入往往能带来最大的排查效率回报。

### 8.5 关于技术选型

**"高复杂度的优化只有在确认瓶颈后才引入"**。路由缓存用 `shared_ptr + atomic_load/store` 而不是 `folly::atomic_shared_ptr`，直方图用固定桶而不是 HDR Histogram，Reactor 用 poll 而不是 epoll——不是因为后者不好，而是因为当前规模下前者的 ROSI（Return on Simplicity Investment）最高。技术选型的黄金法则：先用最简方案验证正确性，再在瓶颈处做定向优化。
